\begin{abstract} 
We mechanize two operational semantics for \prologP with cut
and prove them equivalent in the Rocq prover. The first semantics
closely models \elpiP's implementation:
it is based on a stack of alternatives and is well suited for studying
optimizations employed by \prologP abstract machines. 
The second semantics is instead based
on And-Or trees, in which the branches pruned by the cut operator are
made explicit.

We use the tree-based semantics to (i) describe introduction and elimination
rules for disjunction in the presence of cut, which (as expected) depart from
those of classical logic, and (ii) reason about the determinacy analysis
introduced in \elpiP version~3.0, which statically identifies computations that
produce at most one result.%
\end{abstract}

\section{Introduction}


\elpiP is a dialect of \lprologP (see \cite{1991miller-pf,Miller_Nadathur_2012,dunchev15lpar,TASSI_2019})
used as an extension language for the \rocqP prover (formerly the \coqP proof
assistant). \elpiP has become an important infrastructure component: several
projects and libraries depend on it~\cite{krebbers25,Trakt,Trocq,Maas2024,fissore2023,fissore2024}.
Other remarkable libraries include the Hierarchy-Builder library-structuring tool~\cite{cohen_et_al:LIPIcs.FSCD.2020.34}
and Derive~\cite{tassi2018,tassi2019,tassi2023}, a program-and-proof synthesis
framework with industrial applications at SkyLabs AI.

Starting with version 3, \elpiP is equipped with a static analysis for
determinacy~\cite{fissore2026} to help users control
backtracking. \rocqP{} users are familiar with functional programming, but
not necessarily with logic programming; in particular, uncontrolled
backtracking is a common source of inefficiency and makes debugging
harder. The determinacy checker allows the user to assert which predicates
should be considered deterministic and then checks that these predicates
behave like functions, i.e., they commit to their first solution and leave
no \emph{choice points} (places where backtracking could resume). A choice
point correspond to an suspended \emph{alternative} in the execution trace.
In the following we use \emph{choice point} and \emph{alternative} as
synonyms.

This paper reports our first steps towards a mechanization, in the \rocqP
prover, of the determinacy analysis from~\cite{fissore2026}.
We focus on the control operator \emph{cut}, which is useful to restrict
backtracking but makes the semantics depart from a pure logical reading.

We formalize two operational semantics for \prologP with cut. The first is a
stack-based semantics that closely models \elpiP's implementation and is
similar to the semantics mechanized by Pusch in \isabelleP~\cite{10.1007/BFb0105415}
and to the model of Debray and Mishra~\cite[Sec.~4.3]{Debray1988}.
This stack-based semantics is a good starting point to study further
optimizations used by standard \prologP abstract machines~\cite{warren1983abstract,1991ait-wam},
but it makes reasoning about the scope of cut difficult. To address
this limitation we introduce a tree-based semantics in which the branches
pruned by cut are explicit and we prove the two semantics equivalent.
Using the tree-based semantics, we then prove some properties about the
impact of evaluating the cut in disjunctive querys. For example, unlike in
classical logic, $q_1 \lor q_2$ is not equivalent to $q_2 \lor q_1$,
since $q_2$ may be cut-away by $q_1$.

Finally, we use the formal semantics to prove the correctness of a static
determinacy analysis~\cite{fissore2026}. Intuitively,
nondeterminism arises when a computation can be completed by applying two
different rules. We exclude this situation in two ways. Firstly, at
most one rule should be used on a given query. This condition is
satisfied if (i) the rules have non-overlapping heads: 
if two heads do not overlap in the inputs they
accept, then no query can unify with both, or if (ii) we account for the
presence of cut in rule premises: once
a rule whose premises contain a cut succeeds, all remaining rules are discarded.
Secondly, each rule of a deterministic predicate should (i) either call functions,
this ensure that no choice point is left after the execution of the premises
of the chosen rule, (ii) or
call relations provided that they are followed by the cut operator, so that
any allocated choice points preceeding the cut are discarded.

We show that if every rule defining a deterministic predicate passes this analysis, 
then any call to that predicate leaves no choice points.

In the entire paper we use \Cref{fig:progx} as our running example, and
we start by describing how we represent a program like that one.
In the concrete syntax, variables are written with capital letters, and
predicate application follows the $\lambda$-calculus style (no
parentheses).

The description of a program is given by the record $\mathbb{P}$ and
is shared by both semantics. A program consists of a list of
rules \coqIn{R} together with a signature environment \coqIn{sigT}.
We delay the descussion of signatures to \cref{sec:determinacy} where we
describe the static analysis that concerns them.

A rule consists of a head term \coqIn{Tm} and a list of premises. Each
premise is an \coqIn{Atom}, i.e. either the cut operator or a predicate
call. Terms \coqIn{Tm} include predicate symbols, data symbols, and variables.
The syntax tree allows variables to be applied and predicates to be mixed with data.
These higher order features play no role in the current paper that focuses on
first order logic programming, but allows future extensions to full $\lambda$Prolog
to be based on the same mechanization.

The set of variables \coqIn{V}, predicates \coqIn{P} and data symbols \coqIn{S}
are countable. We represent substitutions
$\Sigma$ as finitely supported maps from variables to terms, using the
finmap library~\cite{finmap}.
The empty substitution is written $\epsilon$.

Since a rule may be applied multiple times, its variables must be
freshened before each application. Accordingly, the backchain function
takes a program, the set of variable names used so far (\FV), a
query term, and the current substitution. It returns an updated
set of variable names together with the list of alternatives, i.e. the
rules that apply. More precisely, for each applicable rule it returns the
rule premises together with an updated substitution obtained by unifying
the rule head with the query term.

In our mechanization, we abstract over the unifier and its properties.
The function \eI{unify} takes two terms $t_1$ and $t_2$, together with a
substitution $\sigma$, as input, and optionally returns a substitution
$\sigma'$ that extends $\sigma$. The expected behavior of \eI{unify} is
the standard one (see for example~\cite[section 2.5]{10.5555/778522.778525}), % or \cite{1991miller-pf}),
limited to the first order.
Therefore, if $t_1$ and $t_2$ unify
under $\sigma$, then $\sigma'~t_1 = \sigma'~t_2$, where
$\sigma~t$ denotes subsitution application and $=$ denotes 
syntactic equality.

\subsection{The cut operator}
\label{sec:cut-op}

There are quite a few variants of the cut operator.
The one we are interested in, i.e. the one used in \elpiP, is known as \emph{hard cut}
(see, e.g., the documentation of \sprologP~\cite{swi-prolog-cut}).
Whenever the \coqIn{backchain} function returns a non-empty list of alternatives,
the first one is explored immediately, while the others are suspended as
choice points. Within a given alternative, premises are processed from
left to right, executing each atom in turn. When a cut is encountered, it
discards (i) all choice points created by \coqIn{backchain} for the current call
and (ii) all choice points created while executing the premises to the left of
the cut.

For example, consider the program in \cref{fig:progx} and the query
$\elpiIn{g 0 R}$.
Both rules for \eI{g} apply to this query. Backchaining therefore returns the
following two alternatives:
\[
  [(\sigma_1, [\eI{r A B, f B C, !}]),\; (\sigma_2, [\eI{f D E, f E F}])]
\]
with
$
  \sigma_1 \coloneq \{\eI{A} \mapsto \eI{0}, \eI{C} \mapsto \eI{R}\}
$
and
$
  \sigma_2 \coloneq \{\eI{D} \mapsto \eI{0}, \eI{F} \mapsto \eI{R}\}
$.
For simplicity, we choose an example where variable refreshing plays no role,
so we do not discuss the set \FV{} any further.

Execution continues with the first premise of the first alternative, namely
\eI{r A B} under $\sigma_1$, i.e. \eI{r 0 B}. The remaining alternatives are
stored as choice points.
Backchaining \eI{r 0 B} returns
$
  [(\sigma_3, []), (\sigma_4, []), (\sigma_5, [\eI{!}])]
$
where
$
  \sigma_3 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{0}\}
$
;
$
  \sigma_4 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{1}\}
$
and
$
  \sigma_5 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{2}\}
$.

The next step of interpretation continues with \eI{f B C} under $\sigma_3$,
that is, \eI{f 0 R}, and leaves $[(\sigma_4, []), (\sigma_5, [\eI{!}])]$ as new choice points.
This time, backchaining fails (no rule for \eI{f} matches input $0$). We
therefore backtrack to the most recently introduced choice point and retry
\eI{f B C} under $\sigma_4$, i.e. \eI{f 1 R}. This succeeds with
$\sigma_6 \coloneq \sigma_4 + \{\eI{R} \mapsto \eI{2}\}$.

We now reach the cut. At this point there are still two unexplored
alternatives: one from the third rule for \eI{r} and one from the second rule
for \eI{g} (respectively, $\sigma_5$ and $\sigma_2$). Both are discarded,
because they were created when, or after, the first rule for \eI{g} was
selected. In contrast, a cut does not discard choice points created earlier;
in this example, there are none.
The final solution is:
$
  \{\eI{A} \mapsto \eI{0}, \eI{B} \mapsto \eI{1}, \eI{C} \mapsto \eI{R},
  \eI{R} \mapsto \eI{2}\}
$.

In \cref{tree-sem,stack-sem}, we provide fully mechanized operational semantics for
\prologP with cut. They differ in how they represent the ongoing computation,
in particular how alternatives are stored and how they are pruned by cut.

\section{And-Or Tree semantics}
\label{tree-sem}
\begin{figure}
    % \input{tex_code/tree_def.tex}
    \begin{coqcode}
Inductive tree ~$\coloneq$~
  | KO | OK                            (* failure and success *)
  | Todo of Atom                       (* unexplored branch *)
  | Or   of option tree & ~$\Sigma$~ & tree ~$\!$~    (* $A \lor B_\sigma$ *) 
  | And  of tree & list Atom & tree.   (* $A \land_{B_0} B$ *)
\end{coqcode}
\label{fig:tree-ty}
\caption{Definition of And-Or tree}
\end{figure}

An And-Or tree is a stratified, variable-width tree, defined in
Rocq as in \cref{fig:tree-ty}.
It consists of two kinds %\marginpar{corner case: prog2.elpi}
of layers that alternate: a disjunctive layer is followed by a conjunctive
layer and vice versa. At the root (a query), the tree records a list of
alternatives (an Or-layer); for each alternative, it records a list of
subqueries to be solved (an And-layer). Intuitively, solving a query requires
solving one alternative in the Or-layer, but all subqueries in the
corresponding And-layer.

The tree is built incrementally. The \coqIn{Todo} node
represents an unexplored branch (an \coqIn{Atom}). When the atom is a
\coqIn{call}, we use the backchaining procedure from
\cref{sec:preliminaries} to compute the two layers to attach to the tree:
alternatives form the Or-layer, and the premises of each applicable rule form
the corresponding And-layer. This expansion step is performed by the
\coqIn{step} procedure described in \cref{sec:step}.

In
addition to the \coqIn{Todo} node we have two distinguished nodes, \koC and
\okC, which represent respectively the smallest failed and successful tree.

The \orC node, written \(A \lor B_\sigma\), represents the addition of an
alternative \(B_\sigma\) to an existing disjunction $A$. The left subtree
\(A\) is optional and is absent once that branch has been fully explored.
The right alternative is paired with a substitution \(\sigma\), which becomes
the current substitution when backtracking to \(B\). %\marginpar{why option and not KO?}

The \andC{} node, written \(A \land_{B_0} B\), represents the addition
of a subquery \(B\) to the first choice point in \(A\). We call
\(B_0\) the \emph{reset point} for \(B\): it represents the
continuation for all alternatives of \(A\) except the first. That is,
when backtracking occurs within \(A\), the subtree \(B\) is replaced by
the atoms in \(B_0\). An example is shown in~\cref{sec:na}.

A graphical representation of a tree is shown in \cref{tree-ex1}. For
compactness, we depict \andC and \orC nodes as $n$-ary (rather than binary),
with children associating to the right. The \koC node acts as the terminating
element of an \orC list, while \okC is the terminating element of an \andC
list.

The tree is constructed incrementally by two recursive
functions, \step and \na. Both traverse the tree depth-first, left-to-right.
The node to be explored in a tree is retrieved thanks to the \pathend (in~\cref{fig:getend}).

\subsection{The \step procedure}\label{sec:step}

The \step procedure takes as input a program, a set of variables, a
substitution, and a tree, and returns an updated set of variables, a
\steptag, and an updated tree.  

The set of variables is assumed to contain all variables occurring in the
tree. It is passed to backchain so that rules can be refreshed correctly.
% This guarantees that any call
% to \emph{backchain} returns a list of atoms whose variables are disjoint from
% the variables of the current working tree.\marginpar{not true in figure:fix + also fix in \cref{sec:cut-op}}

The \steptag (see~\cref{fig:signaturesT}) indicates which kind of step was
performed.  \cI{Failure} and \cI{Success} are returned for trees that satisfy,
respectively, the \failed and \success tests. 
\cI{CutBrothers}
indicates the interpretation of a superficial cut: \step was called on an 
And-layer and its \pathend is the cut atom. Finally, \cI{Expanded}
accounts for the interpretation of predicate calls and non-superficial cuts.

The \step procedure evaluates atoms. In particular, it leaves the tree
unchanged when the tree is \emph{success} or \emph{failed}.

\subsection{The \run inductive}\label{sec:runT}

The inductive relation \run relates four inputs to three outputs. The inputs
are a program, a set of variables, an initial substitution $\sigma$, and a
tree $t$. The outputs are an optional result $r$, a boolean $b$, and an updated set of variable
names.

The main result $r$ is $\mnone$ when the execution fails; otherwise
when $r = \msome(\sigma', t')$ the execution succeeded and produced the solution
$\sigma'$; $t'$ represents the remaining, not-yet-explored alternatives. 
The boolean $b$ records whether a
superficial cut was evaluated during execution.
% , and the updated variable set tracks freshly generated names.

The \run predicate has four cases, depicted as inference rules in \cref{fig:run-rules}.
(\stopt) If \pathend\ $t$ is a success, then the substitution
$\sigma'$ is extracted from $t$ (starting from $\sigma$) and the input tree is
cleaned of its successful path. (\stept) If \pathend\ $t$ is an atom,
then \step is invoked to evaluate $t$, and \run is called recursively on the
updated tree. (\backt) If \pathend\ $t$ is a failure, then \na is
called to clear the failed path; if the resulting cleaned tree exists, \run is
called recursively on it. Finally, (\failt) accounts for trees with no
solutions.

\Cref{th:runSSTor,th:runNTor,th:runNFor} correspond to the introduction rules
for disjunction. If $A$ executes a cut, one \emph{cannot} obtain $A \lor B$ from
$B$: the execution of $A$, whether it ultimately succeeds or fails, makes the
success of $B$ irrelevant (the cut discards it). In the first lemma, $B$ is
forced to be \koC; in the second one, the failure of $A$ absorbs $B$. The last
lemma is connected to the depth-first exploration of the tree: proving a
disjunction from its right-hand side can only occur after the left-hand side
has been disproved.

If $A$ does not cut, the elimination rule has the usual two premises, together
with the additional constraint that whenever $B$ holds, $A$ must have failed.
This again reflects the depth-first traversal of the proof tree.

  \noLine

It is worth recalling that the “$A$ cuts” side-condition in the rules above is
precisely the boolean result returned by \run. Without that information, it is
impossible to formulate these rules: it is not merely a matter of whether $A$
contains a syntactic occurrence of cut, but whether that cut is actually
executed during the (dis)proof of $A$ (in rules $\lor_{ir1}$ and $\lor_{ir2}$).
Indeed, an atom preceding the cut may fail, so the cut is never reached.

As anticipated in the introductionction these lemmas contradict the commutativity of
disjunction.

\section{Stack-based semantics}
\label{stack-sem}

The stack-based semantics we present is very close to what is
implemented by the \elpiP interpreter. This semantics is 
similar to the one proposed by Pusch in
\cite{10.1007/BFb0105415}, which is in turn closely related to the
semantics given by Debray and Mishra in
\cite[Section~4.3]{Debray1988}. Pusch mechanized this
semantics in Isabelle/HOL, together with several optimizations that are
also present in the Warren Abstract Machine
\cite{warren1983abstract,1991ait-wam}.

The execution state is a stack of alternarives.
Each alternative is a list of goals. Intuitively it amounts to
a disjunctive normal form: each stack item is a self contained
computation, coupling a substitution with all the goals to be
solved.

Goals pair an atom with a list of the \emph{cut-to} alternatives, 
making the two datatypes mutually recursive, but these alternatives have a very different role. They have to be understood
as pointers to lower levels of the stack itself. This datum is used to implement the cut, i.e. to prune the stack of alternatives.

The rule system for \nur is given in \cref{fig:nur-rules} and is made by $4$
cases. We distinguish two main cases. If we run out of alternatives
we fail: (\fails) stops the execution and return $\mnone$.
If the list of alternatives is $(\sigma_0, h) :: a$, then
we look at the list of goals $h$ (under the substitution $\sigma_0$). If $h$ is empty, (\stops) stops the execution with a success $\sigma_0$
leaving $a$ as the unexplored alternatives.
If $h$ is not empty we look at its head goal $(t, ca)$ where $t$ is the atom and $ca$ is its
cut-to alternatives. If $t$ is a cut rule
(\cuts) continues to evaluate the tail of $h$ under with alternatives $ca$. Finally, when $t$ is a call, rule (\calls) backchains:
for each rule it pairs each premise with the current stack of
alternatives, and prepents the obtained goals to the tail of $h$.
Note that if backain returns the empty list, (\calls) second
premise amounts to exploring the next item in the current
stack.

\subsection{Inadequacy of the stack-based semantics for formal reasoning}

The lemmas that we presented in
\cref{sec:run-prop} are hard to express in the stack-based semantics, due to the
lack of structure in the stack to delimit the scope of the cut operator. For
example, consider a stack $a_0, a_1, \dots, a_n$. If $a_0$ succeeds but executes a
cut, it is hard to relate the remaining alternatives $a_1, \dots, a_n$ to the
alternatives $b_1, \dots, b_m$ that survive the cut, since the only simple
invariant is that $b_1, \dots, b_m$ is a suffix of $a_1, \dots, a_n$. If
$a_1, \dots, a_n$ were generated before the call whose execution generates the cut
in $a_0$, then they all stay; but if some were generated afterwards, they are
discarded. Expressing this precisely would require attaching, at the very least,
time-stamps (or depths) to goals, which amounts to a cumbersome encoding of a
tree.

\subsection{From trees to stacks}\label{sec:t2l}

The \ttl recursive function translates a tree to a stack.
For space constraints %\marginpar{DAVVERO?}
\cref{fig:ttl} only gives the base cases, while we
describe the recursive cases in the following text.
% we give junst the implementation of the
% base cases, the full implementation is available at \href{https://github.com/FissoreD/elpi-formalization/blob/ho-check-ffun/theories/t2l.v}{\emph{this}} link.

The function \ttl takes as input the tree $t_0$, a substitution
$\sigma_0$, and a list of choice points $cp$. These choice points
represent alternatives that appear at the same level of the current
tree, such as, for example, the right siblings of an \orC{} node. The
substitution is used to determine under which substitution the
subtree being computed lives.

The \okC node represents one successful alternative; therefore it is translated
into a singleton list whose only element has an empty list of goals. The \koC
node represents failure, hence it is mapped to the empty list of alternatives.
Finally, atoms are mapped to a singleton list containing one alternative whose
only goal is that atom, with an empty cut-to list.
At this stage, the cut-to list cannot point to $cp$: atoms are not
right-uncle subtrees, whereas $cp$ represents alternatives that will actually
be discarded if the atom turns out to be a cut. The correct cut-to list is
therefore determined later, once the trees corresponding to sibling subtrees
have been inspected.

The translation of $A \lor B_\sigma$ creates two list of alternatives,
one for the $A$ and the other for $B$. The alternatives of $B$ are valid
choice points for $A$ and should be passed to the translation of $A$.
The two lists of alternatives can then be concatenated. Moreover, every atom
occurring one level below $cp$ (i.e. in $A$ or $B$) should add $cp$ as its
cut-to alternatives.

The translation of $A \land_{B_0} B$ starts with the translation of $A$. If the
translation of $A$ is an empty list we return the empty list of
alternatives without even touching $B$ nor $B_0$, since an empty
translation for $A$ indicates failure and this in turn implies the
failure of the entire conjunction. When the translation of $A$ is
a list $(\sigma_0, g) :: a$, the $B$ node represents the continuation of the
first alternative $g$, whereas $B_0$ is the continuation for each alternative
in $a$.

\section{Case study: determinacy alanysis}\label{sec:determinacy}

An interesting application of the tree semantics is determinacy checking,
introduced in version~3 of the \elpiP{} language~\cite{fissore2026}. The
checker takes as input the signatures of the predicates declared by the
user and verifies that the rules of a deterministic predicate generate at
most one solution; we call this particular kind of predicate a function.
Thanks to this static verification, the user can better control
unexpected backtracking statically.

A predicate behaves deterministically if two conditions are
satisfied: \emph{mutual exclusion} guarantees that at most one rule can
be successfully applied to any given query, whereas \emph{rule checking}
ensures that each rule does not create choice points, for example by
calling non-deterministic predicates.

Determinacy checking is strongly related to the modes of predicates: we
differentiate between input and output arguments. A deterministic call relates to its inputs only one
output. In the literature, we find several works about determinacy checking,
namely~\cite{1996Somogy,king2005,1989Warren}. These works needs a mode checker
statically ensuring that in a query with ground inputs, each recursive
call is performed with ground inputs.

\section{Related work}

We studied a \prologP semantics in which input arguments are \emph{matched},
rather than unified, against rule heads. This choice agrees with the \elpiP
interpreter, which is in turn inspired by B-Prolog's
``matching-clauses''~\cite{1991ait-wam,zhou2012}. The two semantics we presented (and
proved equivalent) also apply to standard \prologP if one forces all predicate
signatures to have only output arguments.

For determinacy analysis, matching input arguments affects the development
only as follows: \cref{th:matchingdisj} does not require the query $q$ to
be ground. Adapting our results to standard \prologP therefore requires
the insertion of two additional hypotheses in
\cref{th:detcheckcall}. First, one has to require that $t$ has ground inputs.
Second, that the program $p$ is well-moded.
Well-moded predicates produce ground outputs when given ground inputs;
hence, starting from an initial query with ground inputs, well-moded
programs behave exactly as if input arguments were matched. Therefore,
the proofs in \cref{sec:determinacy} still apply.

The only mechanization of Prolog's semantics
we could find is the one by Pusch in \isabelleP~\cite{10.1007/BFb0105415}
that is based on the model of Debray and Mishra~\cite[Sec.~4.3]{Debray1988}.
Their work starts from that semantics and refines it by
introducing some optimizations usually found in
the Warren abstract machine~\cite{warren1983abstract,1991ait-wam}.
They do not use the semantics to prove properties
on the execution of programs as we do in our use case, hence they do not face the
difficulty described in \cref{stack-sem} that pushed us to
develop a more explicit semantics (with respect to cut).
In a sense, our work is complementary, showing the stack-based semantics
equivalent to a more optimized one.

Another relevant work is by King~\cite{2011king},
but we could not find their Rocq source code. Their semantics
is denotational and cannot easily cover all the
features our paper covers, but it would have
been sufficient for this first step.

The proof technique we use to relate the two semantics is inspired by
\cite{yves-equiv}, and we thank Y.~Bertot for insightful discussions on
the topic. In \cite{yves-equiv}, Bertot mechanizes the correctness of a
compiler. He relates the semantics of an imperative language to that of
its compiled assembly code and proves their equivalence. His approach
uses the compiler as the translation function from one language to the
other, but does not introduce a decompiler, just as we do not define a
function from stacks to trees.
To show that the assembly code behaves like the imperative language, he
proceeds by induction on the execution of the assembly program. We adopt
the same strategy in the proof of \cref{th:elpitotree}.

\section{Conclusion}

This paper describes two operational semantics for Prolog with cut. The first
semantics is based on And--Or trees: it is well suited to graphically
illustrating the scope of cut, and to proving lemmas about the impact of its
evaluation when reasoning about disjunctions. The second semantics is based on
a stack of alternatives: it is computationally more efficient, but it loses the
structural expressiveness of the tree-based semantics. Thanks to a dedicated
function, we translate trees into stacks and prove the two semantics equivalent.
This stack-based semantics corresponds to the first-order fragment of \elpiP.
Using the tree-based semantics, we mechanize the first-order part of the
determinacy checker that has been available in \elpiP since version~3.0, and we
prove that a call to a deterministic predicate returns at most one solution.

The formal development consists of approximately 2,500 lines of
specifications and about 5,000 lines of \textit{ssreflect} proofs. Roughly 30\%
of the code is dedicated to the tree semantics (in particular, the proofs in
\cref{sec:runT}), 15\% to the stack semantics, and 35\% to the equivalence proof.
The remaining 20\% is devoted to the determinacy checker. The development took
approximately $8$ months.

To fully model the \elpiP language, we would need to account for higher-order
variables, i.e. variables representing predicates. This extension is ongoing and
largely orthogonal to the present paper, since cut and higher-order features do
not interact in subtle ways.
