\begin{abstract} 
We mechanize two operational semantics for \prologP with cut
and prove them equivalent, in the Rocq prover. The first semantics
closely models the \elpiP's implementation,
it is based on a stack of choice points and is well suited for studying
optimizations employed by \prologP abstract machines. 
The second semantics is instead based
on and-or trees, in which the branches pruned by the cut operator are
made explicit.

We use the tree-based semantics (1) to prove properties about the effect of
the cut operator in the evaluation of choice points, since the
rules from classical logic do not apply, and (2) to reason about the determinacy
analysis introduced in Elpi version~3.0, which statically identifies
computations that produce at most one result.%
\end{abstract}

\section{Introduction}


\elpiP is a dialect of \lprologP (see \cite{1991miller-pf,Miller_Nadathur_2012,dunchev15lpar,TASSI_2019})
used as an extension language for the \rocqP prover (formerly the \coqP proof
assistant). \elpiP has become an important infrastructure component: several
projects and libraries depend on it~\cite{krebbers25,Trakt,Trocq,Maas2024,fissore2023,fissore2024}.
Other remarkable libraries include the Hierarchy-Builder library-structuring tool~\cite{cohen_et_al:LIPIcs.FSCD.2020.34}
and Derive~\cite{tassi2018,tassi2019,tassi2023}, a program-and-proof synthesis
framework with industrial applications at SkyLabs AI.

Starting with version 3, \elpiP is equipped with a static analysis for
determinacy~\cite{fissore2026} to help users control
backtracking. \rocqP{} users are familiar with functional programming, but
not necessarily with logic programming; in particular, uncontrolled
backtracking is a common source of inefficiency and makes debugging
harder. The determinacy checker allows the user to assert which predicates
should be considered deterministic and then checks that these predicates
behave like functions, i.e., they commit to their first solution and leave
no \emph{choice points} (places where backtracking could resume). A choice
point correspond to an suspended \emph{alternative} in the execution trace.
In the following we use \emph{choice point} and \emph{alternative} as
synonyms.

This paper reports our first steps towards a mechanization, in the \rocqP
prover, of the determinacy analysis from~\cite{fissore2026}.
We focus on the control operator \emph{cut}, which is useful to restrict
backtracking but makes the semantics depart from a pure logical reading.

We formalize two operational semantics for \prologP with cut. The first is a
stack-based semantics that closely models \elpiP's implementation and is
similar to the semantics mechanized by Pusch in \isabelleP~\cite{10.1007/BFb0105415}
and to the model of Debray and Mishra~\cite[Sec.~4.3]{Debray1988}.
This stack-based semantics is a good starting point to study further
optimizations used by standard \prologP abstract machines~\cite{warren1983abstract,10.7551/mitpress/7160.001.0001},
but it makes reasoning about the scope of cut difficult. To address
this limitation we introduce a tree-based semantics in which the branches
pruned by cut are explicit and we prove the two semantics equivalent.
Using the tree-based semantics, we then prove some properties about the
impact of evaluating the cut in disjunctive querys. For example, unlike in
classical logic, $q_1 \lor q_2$ is not equivalent to $q_2 \lor q_1$,
since $q_2$ may be cut-away by $q_1$.

Finally, we use the formal semantics to prove the correctness of a static
determinacy analysis~\cite{fissore2026}. Intuitively,
nondeterminism arises when a computation can be completed by applying two
different rules. We exclude this situation in two ways. Firstly, at
most one rule should be used on a given query. This condition is
satisfied if (i) the rules have non-overlapping heads: 
if two heads do not overlap in the inputs they
accept, then no query can unify with both, or if (ii) we account for the
presence of cut in rule premises: once
a rule whose premises contain a cut succeeds, all remaining rules are discarded.
Secondly, each rule of a deterministic predicate should (i) either call functions,
this ensure that no choice point is left after the execution of the premises
of the chosen rule, (ii) or
call relations provided that they are followed by the cut operator, so that
any allocated choice points preceeding the cut are discarded.

We show that if every rule defining a deterministic predicate passes this analysis, 
then any call to that predicate leaves no choice points.

Both semantics share the same notion of program, written $\mathbb{P}$.
\Cref{fig:progx} is our running example. A program consists of a list of
rules \coqIn{R} together with a signature environment \coqIn{sigT}. Besides
the arity of each predicate, a signature specifies which arguments are
inputs and which are outputs, and whether the predicate is deterministic.
Inputs come before outputs.

A rule consists of a head term \coqIn{Tm} and a list of premises. Each
premise is an \coqIn{Atom}, i.e. either the cut operator or a predicate
call. Terms \coqIn{Tm} include predicate symbols, data, and variables. In
the concrete syntax, variables are written with capital letters, and
predicate application follows the $\lambda$-calculus style (no
parentheses).

The set of variables \coqIn{V} is countable. We represent substitutions
$\Sigma$ as finitely supported maps from variables to terms, using the
finmap library~\cite{finmap}.
The empty substitution is written $\epsilon$ while
the composition of two substitutions $\sigma_1$ and $\sigma_2$ with
disjoint supports as $\sigma_1 + \sigma_2$.

The backchaining operation applies all rules to a query term; it is
central to both semantics.

\subsection{The cut operator}
\label{sec:cut-op}

The cut operator in \textsc{\elpiP} implements the \emph{hard cut}
(see, e.g., the documentation of \textsc{SWI-Prolog}~\cite{swi-prolog-cut}).
Whenever the backchaining function \coqIn{bc} returns a list of alternatives,
the first one is explored immediately, while the others are suspended as
\emph{choice points}. Within a given alternative, premises are processed from
left to right. When a cut is encountered, it discards (i) all choice points
created by \coqIn{bc} for the current call and (ii) all choice points created
while executing the premises preceding the cut.

For example, consider the program $P$ in \cref{fig:progx} and the query
$\elpiIn{g 0 R}$.
Both rules for \eI{g} apply to this query. Backchaining therefore returns the
following two alternatives:
\[
  [(\sigma_1, [\eI{r A B, f B C, !}]),\; (\sigma_2, [\eI{f D E, f E F}])]
\]
with
$
  \sigma_1 \coloneq \{\eI{A} \mapsto \eI{0}, \eI{C} \mapsto \eI{R}\}
$
and
$
  \sigma_2 \coloneq \{\eI{D} \mapsto \eI{0}, \eI{F} \mapsto \eI{R}\}
$.
For simplicity, we choose an example where variable refreshing plays no role,
so we do not discuss the set \FV{} any further.

Execution continues with the first premise of the first alternative, namely
\eI{r A B} under $\sigma_1$, i.e. \eI{r 0 B}. The remaining alternatives are
stored as choice points.
Backchaining \eI{r 0 B} returns
$
  [(\sigma_3, []), (\sigma_4, []), (\sigma_5, [\eI{!}])]
$
where
$
  \sigma_3 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{0}\}
$
;
$
  \sigma_4 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{1}\}
$
and
$
  \sigma_5 \coloneq \sigma_1 + \{\eI{B} \mapsto \eI{2}\}
$.

The next step of interpretation continues with \eI{f B C} under $\sigma_3$,
that is, \eI{f 0 R}, and leaves $[(\sigma_4, []), (\sigma_5, [\eI{!}])]$ as new choice points.
This time, backchaining fails (no rule for \eI{f} matches input $0$). We
therefore backtrack to the most recently introduced choice point and retry
\eI{f B C} under $\sigma_4$, i.e. \eI{f 1 R}. This succeeds with
$\sigma_6 \coloneq \sigma_4 + \{\eI{R} \mapsto \eI{2}\}$.

We now reach the cut. At this point there are still two unexplored
alternatives: one from the third rule for \eI{r} and one from the second rule
for \eI{g} (respectively, $\sigma_5$ and $\sigma_2$). Both are discarded,
because they were created when, or after, the first rule for \eI{g} was
selected. (In contrast, a cut does not discard choice points created earlier;
in this example, there are none.)

The final solution is:
$
  \{\eI{A} \mapsto \eI{0}, \eI{B} \mapsto \eI{1}, \eI{C} \mapsto \eI{R},
  \eI{R} \mapsto \eI{2}\}
$.

In \cref{tree-sem,stack-sem}, we provide fully mechanized operational semantics for
\prologP with cut. They differ in how they represent the ongoing computation,
in particular how alternatives are stored and how they are pruned by cut.

An And-Or tree is a stratified, variable-width tree. It consists of two kinds\marginpar{corner case: prog2.elpi}
of layers that alternate: a disjunctive layer is followed by a conjunctive
layer and vice versa. At the root (a query), the tree records a list of
alternatives (an Or-layer); for each alternative, it records a list of
subqueries to be solved (an And-layer). Intuitively, solving a query requires
solving one alternative in the Or-layer, but all subqueries in the
corresponding And-layer.

The tree is built incrementally. The \coqIn{Todo} node
represents an unexplored branch (an \coqIn{Atom}). When the atom is a
\coqIn{call}, we use the backchaining procedure from
\cref{sec:preliminaries} to compute the two layers to attach to the tree:
alternatives form the Or-layer, and the premises of each applicable rule form
the corresponding And-layer. This expansion step is performed by the
\coqIn{step} procedure described in \cref{sec:step}.

The Rocq data type for And-Or trees is given in \cref{fig:tree-ty}. In
addition to \coqIn{Todo}, it provides two distinguished nodes, \koC and
\okC, which represent respectively the smallest failed and successful tree.

The \orC node, written \(A \lor B_\sigma\), represents the addition of an
alternative \(B_\sigma\) to an existing disjunction $A$. The left subtree
\(A\) is optional and is absent once that branch has been fully explored.
The right alternative is paired with a substitution \(\sigma\), which becomes
the current substitution when backtracking to \(B\).\marginpar{why option and not KO?}

The \andC node, written \(A \land_{B_0} B\), represents the addition of a
subquery \(B\) to be solved after \(A\). We call \(B_0\) the \emph{reset
point} for \(B\): it is used to restore the initial state of \(B\) when
backtracking occurs within \(A\). An example is shown in \cref{sec:na}.

A graphical representation of a tree is shown in \cref{tree-ex1}. For
compactness, we depict \andC and \orC nodes as $n$-ary (rather than binary),
with children associating to the right. The \koC node acts as the terminating
element of an \orC list, while \okC is the terminating element of an \andC
list.

\subsection{The tree-based semantics}

The tree is constructed incrementally by two recursive
functions, \step and \na. Both traverse the tree depth-first, left-to-right.
The node to be explored in a tree is retrieved thanks to the \pathend (in~\cref{fig:getend}).
In the snippet we also identify special kinds of trees: depending on
the \pathend, we distinguish between \emph{success}, \emph{failed} and
\emph{incomplete} trees.
Since all functions must terminate in Rocq, we define their transitive closure
as the inductive relation \run.

Intuitively, \run iterates calls to \step on incomplete trees to evaluate
the \cI{Todo} node. Upon failed trees, it calls \na to find
the next
alternative and continues from there, if one exists. We detail \step, \na, and
\run in \cref{sec:step,sec:next_alt,sec:runT}.

\subsection{The \step procedure}\label{sec:step}

The \step procedure takes as input a program, a set of variables, a
substitution, and a tree, and returns an updated set of variables, a
\steptag, and an updated tree.  

The set of variables is assumed to contain all variables occurring in the
tree. It is passed to backchain so that rules can be refreshed correctly.
% This guarantees that any call
% to \emph{bc} returns a list of atoms whose variables are disjoint from
% the variables of the current working tree.\marginpar{not true in figure:fix + also fix in \cref{sec:cut-op}}

The \steptag (see~\cref{type:steptag}) indicates which kind of step was
performed.  \cI{Failure} and \cI{Success} are returned for trees that satisfy,
respectively, the \failed and \success tests. 
\cI{CutBrothers}
indicates the interpretation of a superficial cut: \step was called on an 
And-layer and its \pathend is the cut atom. Finally, \cI{Expanded}
accounts for the interpretation of predicate calls and non-superficial cuts.

The \step procedure evaluates atoms. In particular, it leaves the tree
unchanged when the tree is \emph{success} or \emph{failed}.

\step expands \coqIn{Todo} nodes by calling backchain, which returns a list
$l$ of alternatives. If $l$ is empty, then the current call is replaced by
\koC. Otherwise, it is replaced by a right-skewed tree of \orC nodes, where
each leaf corresponds to a list of atoms $e \in l$. If $e$ is empty, the leaf
is \okC; otherwise, it is a right-skewed tree of \andC nodes.

\subsubsection{The interpretation of a cut}

The step corresponding to a cut performs two actions: (i) the cut node is
replaced by \okC; and (ii) the subtrees in the scope of \cutC are pruned. More
precisely, (ii) prunes the left siblings of the \cutC node (in the same
And-layer, denoted \cutl) and prunes the right uncles of \cutC (in the
one-level-up Or-layer, denoted \cutr).

\subsection{The \run inductive}\label{sec:runT}

The inductive relation \run relates four inputs to three outputs. The inputs
are a program, a set of variables, an initial substitution $\sigma$, and a
tree $t$. The outputs are (i) an optional result $r$ of the form
$\msome(\sigma', t')$, (ii) a boolean $b$, and (iii) an updated set of variable
names.

The main output is $r$: if $r = \mnone$, interpretation fails; otherwise
$\sigma'$ is the computed solution substitution and $t'$ represents the
remaining, not-yet-explored alternatives. The boolean $b$ records whether a
superficial cut was evaluated during execution, and the updated variable set
tracks freshly generated names.

\run has four cases, depicted as inference rules in \cref{fig:run-rules}.
(\textsc{StopT}) If \pathend\ $t$ is a success, then the substitution
$\sigma'$ is extracted from $t$ (starting from $\sigma$) and the input tree is
cleaned of its successful path. (\textsc{StepT}) If \pathend\ $t$ is an atom,
then \step is invoked to evaluate $t$, and \run is called recursively on the
updated tree. (\textsc{BackT}) If \pathend\ $t$ is a failure, then \na is
called to clear the failed path; if the resulting cleaned tree exists, \run is
called recursively on it. Finally, (\textsc{FailT}) accounts for trees with no
solutions.

These rules are deterministic:

\input{tex_code/runT_det.tex}

The proof is by induction on the first \run derivation and is immediate,
because the rules are selected based on \pathend\ $t$. In particular, the
hypotheses \emph{success $t$}, \emph{\pathatom $t$}, and \emph{failed $t$} are
mutually exclusive. Moreover, by \cref{lemma:runTdet}, the hypothesis of
\textsc{FailT} implies \emph{failed $t$}; hence \textsc{FailT} is exclusive
with \textsc{StopT} and \textsc{StepT}, and it is also exclusive with
\textsc{BackT} since they impose different requirements on the output of \na.

\section{Stack semantics}
\label{stack-sem}

We now introduce the stack semantics. The interpreter is close to that
of the \elpiP language and provides an operational semantics that is
similar to the one proposed by Pusch in
\cite{10.1007/BFb0105415}, which is in turn closely related to the
semantics given by Debray and Mishra in
\cite[Section~4.3]{Debray1988}. Pusch mechanized this
semantics in Isabelle/HOL, together with several optimizations that are
also present in the Warren Abstract Machine
\cite{warren1983abstract,10.7551/mitpress/7160.001.0001}.

We represent a state of the \elpiP language thanks to the two
mutual inductives shown below.

\input{tex_code/elpi_def.tex}

A stack is an enhanced two-dimensional list, called \emph{alts} in the
inductive. The outermost list
represents a list of alternatives in disjunction, each accompanied by
the substitution that should be used for their interpretation. The
innermost list is a list of atoms, that is, the list of goals in
conjunction. These goals are decorated with a pointer to an alternative
list, which is used to keep track of where to jump when a cut is
interpreted. We call these special alternatives the \emph{cut-to}
alternatives.

what is the scope of the cut operator. For example, in a stack made of
these alternatives $a_0, a_1 \dots a_n$, we have no clear idea of what happens
if the first alternative $a_0$ succeeds: there could be a cut in $a_0$ but, is
this cut superficial? What is its impact wrt the alternatives $a_1 \dots a_n$?
More then that, it is also possible that the state is hill-formed and the cut
does not point to a suffix in the list of alternatives.

\section{Equivalence of the two semantics}

In order to relate the two semantics we have to relate the computations states,
i.e., the And-Or tree and the stack of alternatives. In particular
we define a translation from trees to stacks, called \ttl.
We do not explcitly provide the converse translation, an economy
allowed by the proof technique we employ, inspired by~\cite{yves-equiv}.

Before describing the translation of trees to stacks (in~\cref{sec:t2l})
we need to define the notion of \emph{valid tree}. The \coqIn{tree}
datatype indeed contains trees that cannot be generated
by \coqIn{runT} via \coqIn{step} or \coqIn{prune}, for example
all the trees that do not correspond to a depth-first left-to-right
tree construction strategy.

The first direction of the equivalence states that the execution of

\begin{proof}
We proceed by induction on the execution of \run'. There are four cases
to consider. The first case arises from \textsc{StopT}; it deals with
successful trees. A successful tree must start with an empty list, and
therefore we conclude using \textsc{StopE}. The case for \textsc{StepT}
requires treating two subcases: \step evaluates either a cut or a call.
Accordingly, we apply \textsc{CutE} or \textsc{CallE}, followed by the
induction hypothesis. The case for \textsc{BackT} is silent: it represents
the non-injective behavior of \ttl; however, thanks to
\cref{th:pruneFt2l} and the induction hypothesis, the conclusion is
proved. The last case arises from the derivation \textsc{FailT}. It is
easily proved using \textsc{FailE} and the fact that if \na returns
$\mnone$ when trying to erase failure in $t$, then \ttl applied to $t$
returns the empty list.
\end{proof}

\section{Case study: determinacy alanysis}\label{sec:determinacy}

An interesting application of the tree semantics is the determinacy checking
that was added in version 3 of the \elpiP langauge~\cite{fissore2026}. The
checker is meant to receive the signature of the predicates declared by the user
and then verify that the rules of a deterministic predicate will return at most
one solution, we define this particular kind of predicate as functions. Thanks
to this static verification, the user can better control unexpected backtracking
at compile time: if an incoherence is rilevata then a fatal error explain why
the current program may break determinacy. A function behaves deterministically
if two main conditions are respected: \emph{mutual exclusion} guarantees that at
most one rule can be successfully used on a given query, whereas \emph{rule
checking} ensure that each rule does not creates choice points, e.g. by calling
non-deterministic predicates.

\section{Related work}

We studied a \prologP semantics in which input arguments are \emph{matched},
rather than unified, against rule heads. This choice agrees with the \elpiP
interpreter, which is in turn inspired by B-Prolog's
``matching-clauses''~\cite{zhou2012}. The two semantics we presented (and
proved equivalent) also apply to standard \prologP if one forces all predicate
signatures to have only output arguments.

For determinacy analysis, matching input arguments affects the development
only as follows: axiom XXX does not require the query $q$ to be ground.
Adapting our results to standard \prologP therefore requires two changes.
First, to add the corresponding groundness hypothesis to XXX. Second, to discharge
this premise when XXX is used. Typically this requires an additional static analysis that
checks whether the program is well-moded. Well-moded predicates produce
ground outputs assuming ground inputs; hence, starting from a ground initial
query, well-moded programs behave exactly as if input arguments were matched,
and hence the proofs in \cref{sec:determinacy} still apply.

The only mechanization of Prolog's semantics
we could find is the one by Pusch in \isabelleP~\cite{10.1007/BFb0105415}
that is based on the model of Debray and Mishra~\cite[Sec.~4.3]{10.1016/0743-1066(88)90007-6}.
Their work start from that semantics and refines it by
introducing some optimizations usually found in
the Warren abstract machine~\cite{warren1983abstract,10.7551/mitpress/7160.001.0001}.
They do not use the semantics to prove properties
on the execution of programs as we do in our use case, hence they do not face the
difficulty described in \cref{stack-sem} that pushed us to
develop an more explicit semantics (with respect to cut).
In some way our work is complementary, showing the stack
based semantics equivalent to a more optmized one.

Another relevant work are the ones by King~\cite{2011king},
but we could not find their Rocq source code. Their semantics
is denotational and cannot easily cover all the
features our paper \cite{fissore2026} does, but would have
been sufficient for this first step.

The proof technique we use to relate the two semantics
is inspired by \cite{yves-equiv} and we thank Y.Bertot for insightful
discussions on the topic. In \cite{yves-equiv} Bertot relates bla bla,
